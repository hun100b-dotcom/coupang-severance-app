## 0. 종훈님 명시 2대 원칙 (최상위 — 모든 단계가 이 순서를 따른다)

> **원칙 ①  기능 최우선 (1순위).** 어드민은 "기능이 실제로 동작하는 것"이 제일이다.
> 모든 네트워크/RLS/엔드포인트 에러를 **먼저 전부 잡아** 실제로 작동하게 만든 뒤에야 디자인을 손댄다.
> **원칙 ②  디자인 톤 통일 (그다음).** 어드민도 **메인 사용자 앱과 똑같은 디자인 톤**(업비트풍, 사용자 화면이 쓰는 `up.*` 토큰·타이포·카드·여백·모션 체계)을 그대로 가져간다.
> **별도 어드민 룩을 새로 만들지 않는다.** 사용자 화면과 "한 몸"처럼 보이게 한다.
>
> → **전체 순서: ① 기능 정상화(에러 박멸·연동 정상화)  →  ② 사용자앱과 동일 톤으로 UI 통일.**
> 디자인 작업(Track B)은 **Track A(기능)가 끝나기 전에는 시작하지 않는다.**

## 2. 핵심 설계 결정 — "연동 원칙"

기존 어드민의 병폐는 **경로 A(supabase 직접·RLS) / 경로 B(백엔드·토큰·RLS우회) 혼재**다. 재개편의 단일 원칙:

> **원칙 1 — 쓰기는 전부 경로 B(백엔드 FastAPI, service-role)로.**
> 어드민의 모든 INSERT/UPDATE/DELETE(공지·문의·공고·지원자·설정·CMS·법정변수·템플릿)는 백엔드 엔드포인트를 통한다. 백엔드는 `_check_admin`(토큰) + (신규) **역할 검사**로 권한을 강제하고, 실패는 4xx로 **명시적으로 반환**한다. → RC3(무음)·RC1(쓰기 403 폭주)·RC6(이원화) 동시 해소.

> **원칙 2 — 관리자 전용 읽기도 점진적으로 경로 B로.**
> 대시보드·목록 등 `is_admin()` 의존 SELECT는 백엔드 집계 엔드포인트로 이전(특히 reports 과소집계 RC2 해결). 단기적으로 직접 SELECT를 유지할 항목은 **반드시 실 OAuth 관리자 세션 전제**임을 명문화.

> **원칙 3 — 프론트 게이트 = RLS 게이트 일치.**
> 입장 판정을 `admin_accounts` 단일 출처로 통일(하드코딩/env 입장 제거 또는 admin_accounts 자동 시드). "게이트는 통과했는데 RLS는 막는" 상태(RC1 프로덕션 변형)를 원천 차단.

> **원칙 4 — 직접 SELECT가 남으면 `.single()` 금지·`.select()` 필수.**
> 잔존 직접 호출은 `.maybeSingle()` + 0행 우아 처리(RC4), 쓰기는 `.select()` + `if(error)` 표시(RC3 방어 2선).

### Phase A1 — 백엔드 쓰기 엔드포인트 구축 (경로 B 단일화 토대)
- **작업**: `backend/app/api/admin.py`에 어드민 쓰기 엔드포인트 신설/정비:

- **파일영역**: `backend/app/api/admin.py`(쓰기 라우트 구역) **단독**. 프론트 무변경.

# ████ TRACK B — 사용자앱과 동일 디자인 톤 통일 (Track A 완료 후) ████

> 원칙 ②. **별도 어드민 룩을 만들지 않는다.** 사용자 화면이 쓰는 `up.*` 토큰·GlassCard·radius·타이포·여백·모션을 **그대로** 어드민에 적용해 "한 몸"으로 만든다.

### 현재 격차(실측) — 무엇이 다른가
| 항목 | 사용자 앱 | 어드민(현재) | 통일 방향 |
|---|---|---|---|
| 토큰 출처 | Tailwind `up.*`(tailwind.config) | `adminTheme.ts`의 `UP` 인라인 객체(값은 `up.*`와 1:1 동일) | **색은 이미 일치** — 출처를 `up.*` 단일화 |
| 카드 | `GlassCard`(backdrop-blur 25px) + `rounded-card`(20) + `shadow-card/float` | 평면 흰카드 `radius 12` + 약한 그림자 | 사용자 카드 폼 채택(데이터밀도 고려해 글래스 강도 조절) |
| 라운드 | `card 20 / btn 12 / sm·md·lg·xl` 스케일 | 대부분 8~14 임의값 | radius 토큰 스케일로 정렬 |
| 타이포 | Pretendard + JetBrains Mono, Tailwind 텍스트 클래스 | Pretendard 동일하나 **인라인 rem**(전역 `.text-* !important` 회피 목적) | 타이포 스케일 통일(아래 제약 주의) |
| 모션 | `page-enter`·`slide-up`·`fade-in` | 거의 없음 | 진입/전환 모션 동일 적용 |
| 여백 | 8pt 그리드 + `max-w-content` | 임의 padding | 8pt 그리드로 정렬 |

> ⚠️ **알려진 제약**: 어드민이 인라인스타일을 쓰는 이유는 전역 `index.css`의 `.text-* !important` 폰트 override 회피였음(adminTheme 주석 명시). Tailwind 텍스트 클래스로 옮길 때 이 override를 함께 해결해야 함 → Track B의 선결 과제.

### Phase B1 — 디자인 토큰 단일 출처화 (시각 변화 최소)
- **작업**: `adminTheme.ts`의 `UP` 객체를 **tailwind `up.*` 토큰을 참조/재노출**하도록 정리(값 중복 제거, 단일 출처). radius/shadow/typography 스케일을 사용자앱 토큰명으로 매핑. 시각적 변화는 최소(리팩터 성격).
- **파일영역**: `components/admin/shared/adminTheme.ts` + (필요시)`tailwind.config.js`(토큰 추가만) + `index.css`의 `.text-* !important` 범위 조정.
- **더블리뷰**: A(토큰 매핑 정확·빌드·시각 회귀 없음) · B(전역 CSS override 변경의 사용자앱 부작용).
- **리스크**: `.text-* !important` 조정이 **사용자 화면 타이포에 영향** → 변경 범위를 어드민 스코프로 한정하고 사용자 화면 회귀 캡처 필수.

### Phase B2 — 공용 카드/버튼/표 컴포넌트를 사용자앱 폼으로 (메뉴 무관, 공통)
- **작업**: 어드민 공용 `adminCard`·버튼·PageHeader·표 헤더를 사용자앱 `GlassCard`/radius/shadow/타이포에 맞춰 재정의(데이터밀도 화면이라 글래스 blur는 약하게·표는 가독 우선). 진입 모션(`page-enter`) 메뉴 전환에 적용.
- **파일영역**: `components/admin/shared/*`(adminTheme·PageHeader 등 공용) **단독**. 개별 메뉴는 공용 토큰만 참조하므로 자동 반영.
- **더블리뷰**: A(사용자앱과 톤 일치·320~1280 무깨짐·AA 대비) · B(데이터밀도 가독성 저하·표 깨짐·모션 과함).
- **리스크**: 표 밀도 화면에 사용자앱 카드를 과적용하면 가독성 저하 → "톤 일치 + 어드민 데이터밀도 유지" 균형. 디자인 더블리뷰에 **스크린샷 비교**(사용자 화면 vs 어드민) 포함.

### Phase B3 — 메뉴별 잔여 인라인 hex/임의값 정리 + 최종 일치 검수
- **작업**: 각 메뉴에 남은 임의 hex·radius·padding을 공용 토큰으로 치환. 사용자 화면과 나란히 놓고 톤 일치 최종 검수.
- **파일영역(배타·순차)**: 메뉴 그룹별(B3a 대시보드·타겟 / B3b 채용군 / B3c 콘텐츠(공지·문의) / B3d 시스템(회원·계정·보안·로그·설정)). 한 번에 한 그룹.
- **더블리뷰**: 그룹별 A(토큰화 완료·시각 회귀 없음) · B(잔여 임의값·다크모드/대비).
- **리스크**: 광범위 치환 회귀 → 그룹별 배타 + 스크린샷 회귀.

> ✅ **Track B 완료 게이트**: 사용자 화면과 어드민을 나란히 캡처해 톤(색·카드·라운드·타이포·모션)이 "한 몸"으로 보이고, 320~1280 무깨짐 + AA 대비 통과.

## 5. 연동 원칙(요약) — 구현 시 강제 규칙
