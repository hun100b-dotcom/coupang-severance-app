### 🔬 근본 원인 규명 — 범인은 **21일 묵은 git lock 파일**

"왜 커밋이 안 됐나"를 추적한 결과, 원인을 특정했습니다.

| 잔존 파일 | 생성 시각 | 의미 |
|----------|----------|------|
| `.git/HEAD.lock` | **2026-08-21 10:09** | **16차 세션**이 남김 |
| `.git/index.lock` | **2026-08-22 10:06** | **17차 세션**이 남김 |
| `.git/objects/maintenance.lock` | 2026-07-16 09:36 | 그 이전부터 잔존 |

- git은 커밋할 때 `.lock` 파일을 만들고, 끝나면 **지웁니다**. 그런데 이 실행 환경(Linux 샌드박스)은 **파일 삭제(unlink)가 차단**되어 있어 git이 자기 lock을 못 지웁니다.
- 그래서 16차가 남긴 `HEAD.lock` 때문에 **17차의 `git commit` 이 `fatal: cannot lock ref 'HEAD'` 로 실패**했고, 17차가 남긴 `index.lock` 때문에 **18차의 `git add` 도 처음엔 실패**했습니다.
- 쉬운 설명: **문에 "작업중" 팻말을 걸고 들어간 사람이 나올 때 팻말을 못 떼서, 다음 사람이 영영 문을 못 여는 상태**였습니다. 16차가 건 팻말이 17차를 막고, 17차가 건 팻말이 18차를 막았습니다.
- **조치: lock 파일을 삭제 대신 `*.stale` 로 이름 변경해 격리**(삭제는 차단되지만 이름 변경은 허용됨)한 뒤 커밋에 성공했습니다 → 커밋 `d5fa4d0`.
- **[신규 P0] 앞으로 스케줄 세션은 git 작업 전 `find .git -name "*.lock"` 로 잔존 lock부터 확인**해야 합니다. 이걸 안 하면 19차·20차도 똑같이 조용히 실패합니다.
